/// Which of `want` queued spawns the `i`-th accepted one should be, when only
/// `take` of them fit in the pool.
///
/// Taking the first `take` in event order is the obvious thing and it is
/// wrong. A saturated block's note-ons span the whole block, so a prefix keeps
/// everything from the opening of the block and drops everything after it --
/// the block is heard at its start and silent at its end, which is a rhythmic
/// artifact at exactly the block rate, built in by construction. Spreading the
/// choice evenly keeps the block's timing intact and merely thins it.
///
/// Both backends call this. Two backends thinning a block differently would
/// not show up as an error, only as two renders that quietly disagree.

[8] src/voice.rs:89
/// The 64-bit key admission ranks queued spawns by, highest kept first.
///
/// `spawn_pick` thins a saturated block evenly, which fixes the rhythmic
/// artifact a prefix causes but is blind to what it is dropping: a fortissimo
/// whole note and a 10 ms grace note have identical odds. On a file that
/// oversubscribes the pool fifteen to one that is most of what you hear.
///
/// The key is two fields, most significant first:
///
/// * **loudness** -- `gain_l + gain_r` quantised to 15 bits. These gains
///   already carry the velocity, the region's own attenuation and its pan, so
///   this is the voice's actual opening amplitude rather than a raw velocity
///   byte.
/// * **position** -- the candidate's index in the block, scrambled, as a
///   tiebreak that carries no information about when the note arrived.
///
/// The scrambled position makes it a total order with no ties, so the admitted
/// set is a pure function of the input and never of scheduling order. Both
/// backends call this. Two backends admitting different notes would not show
/// up as an error, only as two renders that quietly disagree.
///
/// **No term in this key may be a function of position in the block.** The key
/// is applied inside time strata whose entire purpose is to keep rank and time
/// independent, so a term correlated with block position defeats the strata
/// and comes out as level movement at the block rate. A third field once sat
/// above loudness and did exactly that; removing it was most of the 0.2.4
/// pumping fix. The development notes have the account and the numbers, and
/// their open question about moving admission to gate-tile granularity is a
/// live reason somebody will come back to this key.
///
/// A duration term is wanted and is missing -- see the development notes. It has to be
/// expressed without reference to the block: `gain * release` is known per
/// region and mentions no boundary.
///
/// Reordering the queue is safe because a voice's position in time is carried
/// by `start_rel`, not by its index: thinning by rank still leaves every
/// admitted note sounding at exactly the frame it should.

[9] src/voice.rs:131
/// The tiebreak field of the ranking keys: a scrambled function of a
/// candidate's position in the block.
///
/// **Any tiebreak built from the candidate index must destroy its low bits,
/// not promote them.** A stereo library loads as two hard-panned mono regions,
/// so every note queues two adjacent candidates -- left at an even index,
/// right at an odd one. A tiebreak that lets bit 0 rise in significance ranks
/// one whole channel above the other, and under saturation admission throws
/// that channel away. Two tiebreaks were tried before this one and both were
/// defects, the second for exactly this reason; the development notes have both.
///
/// An avalanche mix satisfies it: consecutive indices scatter, so channel
/// parity carries no rank. It is a bijection on 48 bits -- xor-shift-right and
/// odd multiplies, both invertible mod 2^48 -- so distinct candidates still
/// get distinct keys and the order stays total with no ties, which is what
/// makes the admitted set a pure function of the input rather than of
/// scheduling.

[10] src/voice.rs:160
/// Quantise a voice's opening gain to the 15 bits `admit_key` has for it.
///
/// **This may not be a linear window onto the gain.** It was
/// `(gain_l + gain_r).clamp(0.0, 1.0) * 32767`, and the clamp saturated
/// against any loud soundfont at unity volume, while a small `--volume`
/// collapsed every voice onto one or two steps at the other end. Either way
/// the field carries no information and the key falls through to its tiebreak
/// -- and it looks ranked while doing it, which is why it hid for so long.
/// the development notes have the measurements.
///
/// Taking the bits costs one shift and has no window at all. An IEEE-754 bit
/// pattern of a positive float is monotonically increasing in the value, and
/// its exponent field is literally log2, so the top 15 bits below the sign are
/// already a logarithmic quantisation covering the entire positive range.
/// Nothing to saturate, nothing to fall outside, and no transcendental in a
/// path that runs about five billion times on a large file.
///
/// Monotonic and exact, so it is a pure function of the gain and both
/// backends and both runs agree.

/// Per-channel controller state, published the same way the note-off gate is:
/// one row per gate tile, which a voice reads for its own channel.
///
/// Neither of these can be resolved on the host the way sustain can. Sustain
/// only changes *when* a note-off is published, and note-offs are already a
/// host table. Bend changes the step of every voice already in the pool, and
/// channel volume changes the gain of every voice already in the pool, and
/// there may be fourteen million of them. So this is the part of the
/// controller set that costs device work.
///
/// It is arranged to cost as little as possible. The two are tracked
/// separately -- a file that bends but never touches volume pays only for the
/// bend -- and if a control sat at unity for the whole block, the render pass
/// is told and skips that work entirely. Both live in one table so that a
/// channel's bend and gains are adjacent rather than in two rows a kilobyte
/// apart.
