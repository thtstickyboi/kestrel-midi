//! Resuming a render of one file (`Job::checkpoint`): what `session::run_inner`
//! saves and how it goes on from it. The per-track renders have their own
//! (`stems`, `mix`); the container and the checks are shared (`resume`).
//!
//! **What is saved.** The render itself, at a block boundary: the driver's state
//! (`Driver::save_state`), the backend's (`Backend::save_state`: the live
//! voices), and the audio written so far. Nothing is rebuilt from the MIDI by
//! playing it again, so a resume costs the load of the soundfont and a seek in
//! the file, not the minutes already rendered.
//!
//! **Where the render is taken.** `Driver::next_block_or_hold` leaves the driver
//! at a boundary when asked after a block is submitted, and the session asks when
//! a checkpoint is due or the render is being stopped. See that for why this is
//! the one state that can be written whole.
//!
//! **The audio.** A WAV is written to `<name>.partial.wav` and the checkpoint
//! names how much of it is whole: a resume cuts the file back to that and goes
//! on, so what was written after the checkpoint is not in it twice. An encoded
//! stream cannot be cut and continued, so for those the float samples fed to the
//! encoder are also kept, in `<checkpoint>.pcm`, and a resume feeds a new
//! encoder the first part of them again: for these formats the cost of a resume
//! is encoding what was rendered, which is a small fraction of rendering it.
//! The file is renamed to its real name only when the render is whole, so one
//! that was cut off never looks like one that was not.
