//! The MIDI merge on worker threads, `MidiStream::set_threads`
//! (the development notes).
//!
//! # What runs where
//!
//! The tracks are split into `K` runs of neighbours, balanced by the bytes each
//! has left to decode. A worker per run decodes its tracks and merges them --
//! the same `Merge` the caller's thread runs when there are no workers -- into
//! chunks of `(tick, event)`, and hands them over through a bounded queue. The
//! caller merges the `K` workers' chunks: with one worker that is taking the
//! next event of a chunk, and with more a heap of `K` keyed `(tick, run)`.
//!
//! So decoding, and the heap of `log2(tracks)` that is the parse's whole cost on
//! a file of thousands of tracks, leave the caller's thread, which is the
//! drain's. What is left on it is a few nanoseconds an event.
//!
//! # Why the order is exactly the one-thread order
//!
//! One merge over every track hands out its events by `(tick, track)`, a track's
//! own events in their order. A worker's merge does the same over its run, so
//! each worker's events are in that order already. The caller's heap breaks a
//! tie on the run, and runs are neighbours: the earlier run's tracks all come
//! before the later's, so a tie between two runs is decided as the tie between
//! their two tracks would be. A merge of streams that are each in the order,
//! by a key that agrees with it, is that order. `tests` checks it event for
//! event on files with every kind of tie.
//!
//! # The checkpoint
//!
//! `MidiStream::save_state` writes where every track is *as the caller has
//! taken them*, which is behind the workers. So every chunk begins with a
//! snapshot of its worker's tracks -- each reader's position and the event it
//! holds, the same thing a saved stream holds -- and a save reads each worker's
//! tracks again from the snapshot of the chunk being taken, for as many events
//! as the caller has taken from it (`Part::replay`). That gives the bytes a
//! stream on one thread would have saved at the same event; the tests compare
//! them at every chunk boundary and in between. The replay checks every event
//! it reads against the chunk, and a difference is an error, never a guess.
//!
//! A snapshot is about 40 bytes a track, and a chunk holds at least 32 events
//! (512 bytes) a track of its run and at least 16,384 in all, so snapshots add
//! a few percent at most to the bytes that pass through -- on a file of
//! thousands of tracks -- and next to nothing on one of a few hundred.
//!
//! Loading a saved state stops the workers and drops what they had read: the
//! readers are set where the state says, and the merge goes back to the workers
//! at the next event.
//!
//! # Memory
//!
//! Bounded per worker, never by the file: `DEPTH` chunks queued, one being
//! filled and one being taken, of 16 bytes an event -- 4 x 256 KiB on a file of
//! a few hundred tracks, 4 x 16 MiB at most. The readers' own windows are the
//! stream's, its share of `READ_BUDGET` (`window_share`); they move to the
//! workers and back, so the workers hold no window the stream did not.
