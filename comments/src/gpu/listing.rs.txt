//! The GPU adapters, listed one backend at a time, each in a process of its own.
//!
//! Listing the adapters is the first thing Kestrel asks of the graphics drivers,
//! and it asks every backend's: Vulkan's loader with the layers other programs
//! install into it, DX12, and OpenGL. A driver that crashes there takes the
//! process with it before anything can be said. On 2026-10-23 a user's discrete GPU
//! (4 GB, so a laptop, with an integrated GPU beside it) ended the guided renderer
//! at "Looking for GPU adapters", 9 s in, with nothing on screen: no error, no
//! log, and no way past it, since every listing opened every backend whatever
//! `--gpu-backend` said.
//!
//! So a front end lists each backend in a child, `kestrel --force-cli
//! list-adapters --backend <name>`, all of them at once, and reads what each
//! prints, a line an adapter. A child that crashes, hangs or fails costs its
//! backend and nothing else: [`Listing::failed`] says how it ended, and in which
//! module, where Windows can say: the child arms FalconEye's crash filter on its
//! stdout, and the lister reads the module from outside while the filter waits,
//! as FalconEye's watcher does for a render. A backend that failed is left out of
//! every later listing and adapter choice in this process ([`avoided`]) unless a
//! render names it. The machine report's self-test has run in a process of its
//! own since 1.3.0 for the same reason (`falconeye::selftest`).
//!
//! A library caller and the tests have no Kestrel executable to start, and list
//! in their own process, as before. [`isolate_with`] is what a front end calls.
