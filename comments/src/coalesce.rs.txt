//! Duplicate-note coalescing, `Config::coalesce`: N note-ons that would build N
//! voices identical in everything but their gain build one, at N times the gain.
//!
//! Black MIDI is made by layering tracks, so the same note is written many
//! times -- same channel, key, velocity, tick and length. Each copy is a voice,
//! and every voice costs admission, a pool slot, render work and, under
//! saturation, a steal. One voice at the summed gain is the same sound up to
//! float rounding: `N * g` does not round as `g + g + ... + g` does. So this is
//! behind a flag and checked by a null test, not by the byte-identity test.
//! the development notes have the brief and the design note.
//!
//! # What makes two note-ons the same voice
//!
//! Everything a voice is built from and everything that acts on it while it
//! sounds. The driver compares the first kind when the second note-on arrives
//! (`GroupKey`: the packed note word, which holds channel, key, velocity,
//! variant, frame, opening row and glide; the preset; the tuning; the epoch,
//! below; and the previewed layers, which is where a `lorand`/`hirand` draw
//! shows). Two such note-ons are on one gate slot, so every channel controller
//! reaches both alike from then on -- with two exceptions that are decided by
//! where an event sits in the stream rather than by its frame:
//!
//! * **an event between them on their tick.** A CC120 there cuts the first and
//!   not the second, and a bend or a gain change gives them different opening
//!   rows. So any event on the channel other than a note bumps the channel's
//!   *epoch*, and a group takes only note-ons of one epoch.
//!
//!   This is a guard more than a need. Everything such an event can change is
//!   caught elsewhere -- an opening row by the note word's `row_bias`, a
//!   preset, variant or tuning by the key, a cut by the release, since a cut
//!   note is released on the cut's tick -- except a cut between two note-ons
//!   that are both released on that tick anyway, and those are notes that end
//!   on the frame they start, which render silent. No case was found where
//!   the epoch changes what is heard; it costs one increment an event, and it
//!   keeps the next event someone teaches the driver from becoming a merge
//!   nobody checked.
//! * **their release.** That is the one input the note-on cannot know, and it
//!   is what [`Lookahead`] is for.
//!
//! # Why a second reader, and not a pre-pass or a voice that splits
//!
//! The driver drains one block of events at a time, and a voice learns its
//! release from the gate tables published later. Of the brief's options:
//!
//! * a whole-file pre-pass is simplest and wrong for a file of billions of
//!   notes, whose decisions would not fit;
//! * a weighted voice that splits when its group's note-offs differ is exact
//!   and needs no look-ahead, but a backend voice would have to spawn a voice
//!   mid-render, which on the GPU is the spawn and compaction passes;
//! * merging in a backend that already knows durations helps that backend only.
//!
//! So this reads the file a second time, ahead of the driver, and pairs each
//! note-on with the event that releases it using **the render's own pairing**:
//! a real `GateTable`, fed the same events in the same order through the same
//! 31-EDO and `--min-velocity` routing, so the j-th note-off at a slot ends the
//! j-th note-on there with the pedals, CC120, CC121 and CC123 exactly as the
//! render has them. What it hands the driver, one per note-on in stream order,
//! is a *release token*: the tick of the event that publishes the note's
//! note-off, or [`EOF`] for one released when the file runs out. Equal ticks
//! are equal frames, and every note-off published by one event lands on that
//! event's frame, so **equal tokens are equal release frames**. A note-on whose
//! token is `None` is not merged.
//!
//! # What bounds it
//!
//! A note-on is decided as soon as it is released, or at the end of its own
//! tick if nothing else was struck on its slot on that tick, which is most of
//! them. The reader holds the decisions between the driver and its own read
//! position. A note that is held longer than `Config::coalesce_window` further
//! note-ons is decided unmerged -- *forced* -- and that is the bound: the
//! reader never holds more than the window, whatever the file. It is a function
//! of the stream alone, never of how far the reader happened to have read, so
//! a render decides the same notes on any run and after any resume.
//!
//! # Where it runs
//!
//! On a thread of its own (`Config::drain_threads`, [`Lookahead`]), which hands
//! the drain its decisions in batches through a bounded queue. That is safe
//! because of the rule above: nothing but the stream decides what the reader
//! hands over, so a reader that is a long way ahead of the drain decides what
//! one in step with it would. The queue adds at most a few hundred KiB to what
//! the window holds. It moved off the drain's thread on 2026-10-16, when
//! coalescing went on by default and its second parse would otherwise have
//! been the drain's to pay (the development notes).
//!
//! # The checkpoint
//!
//! Rebuilt, not saved. At a block boundary no note-on of a block that is still
//! to come shares a tick with one already drained (a tick is one frame), and
//! the decision for a note-on depends only on the events from it on and on the
//! pairing state when it arrived, which the gate table and the note pairing of
//! `--min-velocity` already save. So [`Lookahead::resync`] puts the reader at
//! the driver's stream position with copies of those, and it decides every
//! later note-on as it would have. A reader running ahead when that happens is
//! stopped first, and what it had decided is dropped: it is decided again.
