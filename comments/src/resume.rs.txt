//! Resuming a per-track render: the checkpoint file, `.krsm`, and what makes
//! one safe to trust.
//!
//! **The requirement, from the development notes:** a resumed
//! render writes the same bytes as an uninterrupted one. That is the
//! determinism rule applied to a stop, and without it a resumed file could not
//! be checked. So a checkpoint is refused, with the reason, rather than
//! guessed at, whenever anything it was made under has changed: the build, the
//! MIDI, a soundfont or one of its sample files, the tracks, the backend and
//! the card, the voice limit.
//!
//! **What a per-track render saves.** No GPU state at all. Each track renders
//! alone and the same bytes whatever lane or thread ran it (`stems`), so a
//! track is either finished -- its file exists, or its blocks are in the mix --
//! or it starts again from its first block. For a merge the mix is an exact
//! integer sum (`mix`), so the order tracks were added in cannot matter.
//!
//! **The one subtlety, which the design note missed.** A track adds its blocks
//! to the mix as it goes, so the running mix already holds part of every track
//! that was in flight. Starting those tracks again from the beginning would add
//! those blocks a second time. So a checkpoint also records, for each
//! unfinished track, how many blocks it had put in the mix, and a resumed track
//! renders from its start but leaves out the blocks the mix already has. They
//! are the same blocks either way, so the sum is exact. The counts and the mix
//! are taken at one instant (`stems` holds the render still for it).
//!
//! **The file** is `KRSMCHK` and a version byte, the header as JSON with its
//! length in front, then the payload (the mix, for a merge; nothing for
//! stems), and last a 64-bit hash of every byte before it. It is written to a
//! temporary name, synced and renamed, so a checkpoint that was cut off is
//! never taken for a whole one; the hash is for the case where the rename was
//! not enough.
