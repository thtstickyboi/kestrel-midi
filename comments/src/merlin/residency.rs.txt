//! Which cached things stay on the card, and which one goes when the room runs
//! out.
//!
//! Merlin has two device caches that used to grow and never shrink -- the
//! kernel cache in [`crate::merlin::fdl`], one entry at ~705 KB, and the head
//! cache in [`crate::merlin::head`], one waveform at up to 1.9 MB. Both filled
//! on real material the moment channel bend joined the cache key (2026-09-07):
//! a standing bend is a resample, so it does not collapse the way duration
//! does, and one 44.75 M-note test file goes from 3,252 distinct entries to
//! **99,270**. At 705 KB that is 71 GiB of kernels against a 2.4 GiB budget,
//! and the head cache filled first -- 769 waveforms against 768 after six
//! seconds of audio, where the whole file used 512 before.
//!
//! ## Why eviction is even allowed
//!
//! Because of the shape of the multiply-accumulate, which is a **forward
//! scatter**: when entry `e` fires at step `t`, `mac` writes
//! `ring[bus][(t+k) % K] += H[e,k] * D[e,t]` for every one of `e`'s lags `k`,
//! all in that step. Its whole tail is deposited in the ring there and then.
//! So **a kernel is needed only during the steps its entry fires in** -- the
//! cache holds *build cost*, not correctness, and a kernel thrown away is a
//! kernel that has to be rebuilt rather than a note that goes missing.
//!
//! A rebuild is bit-identical, which the byte-identity requirement needs:
//! `Kernel::segment` reads `[skip, skip + depth * P)` of a sustain render that
//! the planner has already grown past that point, and `transform` is a fixed
//! schedule. The same argument covers a head row, which is a prefix of the same
//! render.
//!
//! ## The policy, and what it is honestly not
//!
//! the development notes section 7 argues for **Belady** -- evict whatever is used
//! furthest in the future -- on the grounds that offline "the whole file is
//! visible". That is true of the *file* and not of this backend: merlin is a
//! streaming [`Backend`](crate::backend::Backend), it learns a note when
//! `spawn` hands it over, and it can only place that note once its note-off has
//! arrived. What it can see ahead is the planned-impulse ring, which is a few
//! blocks. True Belady wants a pre-scan pass that does not exist.
//!
//! So this is **LRU with the visible future used as a tiebreak**, which is the
//! most Belady the available information supports:
//!
//! 1. Anything needed by the step being encoded is **pinned** and cannot go.
//! 2. Among the rest, an id with **no planned use at all** goes before one that
//!    has some. `pending` is a plain counter maintained per planned note, so
//!    this costs nothing per note -- a per-step scan of the ring to find the
//!    exact next-use step would cost more than the convolution.
//! 3. Within a class, least recently used, with the id as a tiebreak so the
//!    victim is a pure function of the input and not of hashing.
//!
//! Step 2 is what the access pattern makes worth having. The development notes
//! measured it as piecewise-constant -- entries sit flat across a passage and
//! jump at a section change -- so the entries a passage has finished with are
//! exactly the ones with no pending impulses, and they leave before anything
//! still in play.
//!
//! ## What it cannot do
//!
//! Nothing here helps if one *step* needs more than the budget at once, because
//! every id it needs is pinned. That is a real limit and the number to design
//! against: the largest test file's peak block fires 3,428 distinct entries,
//! which is 2.55 GiB -- the entire budget, resident simultaneously. The caller
//! reports that as its own failure rather than thrashing towards it.

/// First fit across the buffers, in order, returning `(buffer, first page)`.
///
/// First fit rather than best fit because the block sizes are few and large: a
/// kernel's depth is its *region's* release tail rounded up to partitions, and
/// a bank has a handful of distinct ones -- the reference bank runs 1.25 s on
/// 54 keys, 1.95-3.0 s on 28 and 4.0 s on 6. A freed run is therefore reused at
/// its own size almost every time, and `put_run`'s coalescing covers the rest.
///
/// A run never straddles a buffer: the multiply-accumulate reads
/// `m.x + k * bins + bin`, so an entry's partitions have to be adjacent, and
/// the alternative is a page table in the hot loop.
