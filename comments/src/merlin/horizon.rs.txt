//! Knowing a note's length before rendering the block it starts in.
//!
//! This is the piece that makes Merlin offline-only, and the dev notes section 4
//! says why in one line: section 3b's collapse works in the **note-on-indexed**
//! form, so the impulse sits at the note-on frame -- but `D` is not known until
//! the note-off, which arrives later in the stream. A block cannot be convolved
//! until every note starting in it has been paired.
//!
//! So this buffers note-ons, pairs them as note-offs arrive, and reports the
//! frame through which everything is resolved. The renderer follows that frame
//! rather than the stream head.
//!
//! ## A lookahead by default, with a pre-scan as the escape hatch
//!
//! The other option is a whole-file pairing pass, which is what `entry_probe`
//! already does, spilling the paired list to disk and reading it back to
//! render. *An earlier version of this comment dismissed that as "cannot hold
//! the result", which was wrong -- it assumed the list had to live in memory.*
//! At 16 bytes a note and the user's measured **5 GB/s sustained read**, it
//! does not:
//!
//! | file | notes | paired list | read back |
//! |---|---|---|---|
//! | 131 s file | 44.8 M | 0.72 GB | 0.14 s |
//! | 366 s file | 824.2 M | 13.2 GB | ~2.6 s |
//! | 20 min file | 2.74 B | 43.9 GB | ~8.8 s |
//!
//! Against the render targets that is roughly 3%, 9% and 6% -- affordable, not
//! free.
//!
//! The lookahead is the default because on this repertoire it costs **nothing**:
//! it holds only the notes currently *open*, and mean note lengths of 1.11 ms
//! and 17.5 ms mean almost nothing is open at once. The buffer is sized by the
//! material's polyphony, not by its note count, so the spill would be gigabytes
//! of I/O to learn what a few kilobytes of state already knows.
//!
//! The spill earns its keep on material the lookahead handles badly: many long
//! notes held simultaneously, where the open set stops being small. That is
//! detectable at runtime rather than guessable -- [`Horizon::open_notes`] is
//! the number, and it is exposed for exactly this.
//!
//! ## The bound is about the kernel cache, not about the horizon
//!
//! A note that is never released would stall the pairing forever, so `max_wait`
//! caps it: past that the note is emitted with its duration clamped, and a
//! later note-off is consumed and discarded so the pairing does not slip.
//!
//! **But the clamp would still be needed with perfect durations from a
//! pre-scan**, which is the part worth keeping straight. It is not about the
//! kernel, though, and this section used to say it was.
//!
//! *Superseded 2026-09-06.* The claim was that a note of duration `D` needs a
//! kernel of `D + release` frames, so a sixty-second note needs a sixty-second
//! kernel and `max_wait` is really the longest note merlin will convolve. That
//! was true of the implementation and is not true of the problem. A kernel
//! holds the note's **release tail**, cached from the reference point `Dj` with
//! the impulse fired `Dj` frames late to match -- see `Kernel::segment` -- so
//! its length is the region's release and nothing else, and it does not vary
//! across a waveform's release buckets either. What a long note costs is the
//! **head cache**: its body is read from there, 4 bytes a frame per waveform,
//! and that is what `merlin_head_frames` bounds.
//!
//! So the bound is still there, it is just somewhere else and an order of
//! magnitude cheaper. Past it a note is clamped rather than dropped: it sounds,
//! and releases, it simply stops early.
