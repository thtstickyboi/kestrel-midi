//! Sustain renders made on the device, many at once: the kernel builder.
//!
//! Every kernel merlin caches starts as one voice rendered with no note-off,
//! the sustain `Kernel::from_cmd` makes with a `CpuSynth`. That is one core
//! rendering one voice after another, and on 2026-10-16 it was the whole of
//! why convolving every note did not work: with `--merlin-promote-after 0` on
//! the 44.75 M-note test file, kernel building had taken **342 s by 76.7 s of
//! audio**, the render was at 0.19x, the GPU was about 6% busy, and the 4 GiB
//! host store that holds the renders was full.
//!
//! This renders a batch of them in parallel on the device, through the same
//! render pass that plays notes on the per-voice backend -- its `SOLO` build,
//! which writes each voice to its own row instead of mixing them (see
//! `render.wgsl` and `GpuSynth::solo_on_shared`). So a kernel built here sounds
//! exactly as the per-voice GPU backend would play that note, which is what
//! the fallback plays the notes that are not convolved with. It is not
//! bit-identical to the `CpuSynth` render, which is a separate implementation
//! of the same arithmetic; `tests/merlin_gpubuild.rs` holds the two together.

/// The most bytes of rows one chunk of a batch lands in: its readback holds
/// every block of every row in it, so this bounds the host memory a chunk in
/// flight takes, and with it how many voices a chunk of long notes may hold.
///
/// *Batches used to be read back 16 blocks at a time, waiting on each read, and
/// before that one block at a time with the whole rows buffer each time --
/// which made the device slower than the CPU it replaces: 13.47 s of building
/// against 6.02 s on the first 30 s of the 44.75 M-note test file with every
/// note convolved, 2026-10-16. A batch is now queued whole and waited on only
/// when something reads it.*
