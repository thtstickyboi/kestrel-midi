//! Key-major merlin, step 1: the bucket pass.
//!
//! THE PLAN's key-major build order (the dev notes, "Proposed: key-major rendering
//! -- flip the loop order") renders one key's notes for the whole song in one
//! pass. So before anything renders, every note has to be known with its
//! length and filed under its key. This is that pass: the real `Driver`
//! against a backend with no pool, the way merlin takes notes, so the pairing
//! and the routing are the render's own rather than a second copy of them.
//! Nothing here renders; `finish` writes silence.
//!
//! What it keeps:
//!
//! - **Runs, not notes.** Copies struck on one slot in one block at one frame,
//!   whose commands differ only in note id and ordinal, are one open run, as in
//!   THE PLAN's Phase 1, and are released from the front a note-off frame at a
//!   time. An open run is 48 bytes where merlin's `Open` holds a whole command.
//! - **A voice table**: one row per distinct command, with everything that
//!   differs per note cleared, and per params generation. Its params and
//!   modulation-envelope rows are **captured by value at the note-on**, since
//!   the driver recycles variant slots and the index alone names a different
//!   table by the time a later step reads it.
//! - **A bucket store**: one list of 40-byte [`RunRec`]s per key, held inside a
//!   fixed memory budget and spilled to a file past it. The budget moves where a
//!   record is held, never which records there are.
//! - **Controller curves**: per channel, the bend and the two channel gains at
//!   each gate tile where they move. Step 3 applies them through a note.
//!
//! ## The gate: what merlin is handed, exactly
//!
//! The pass mirrors `MerlinSynth::route` and `resolve`: the glide rule,
//! `apply_channel`, the promotion count, the release frame, the gain at the
//! note-off, CC120's cut and the head-cache clamp. With `--merlin-digest` it
//! keeps a [`NoteDigest`] of what merlin would plan, copy by copy, and merlin
//! keeps the same digest of what it does plan. **The two agreeing on a real
//! file is step 1's gate.** A second digest covers every note with no clamp and
//! no routing. It is taken as records are filed and again as the store is read
//! back, so a spill that lost or altered a record shows as well.
//!
//! ## What it does not do yet
//!
//! Glides are stripped and flagged ([`REC_GLIDE`]); step 4 gives them their own
//! path. Records within a key come out in release order, not start order; the
//! window step (5) sorts them. Curves are held in memory and counted, not
//! spilled.
