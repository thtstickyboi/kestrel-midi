        // nothing else -- a 26-track file at 43M events/sec against a
        // 4,393-track one at 17.4M, a 2.47x spread where the depth ratio is
        // 2.57. A file is not slow to read because it is big; it is slow
        // because of its track count.
        //
        // The gain beats the 2x the operation count suggests, because in a
        // k-way merge over MIDI tracks the same dense track is repeatedly the
        // minimum: the popped element sifted all the way down and the pushed
        // one climbed all the way back to the root. Replacing in place lets
        // the sift-down exit early, since the next event from that track is
        // usually still the smallest.

/// Converts ticks to absolute output frames the way BASSMIDI does, tracking
/// tempo changes as they arrive in the merged stream.
///
/// **Not the textbook tick arithmetic, on purpose.** BASSMIDI advances MIDI
/// time one whole output sample at a time. An event -- a tempo change included
/// -- fires on the first sample whose tick position has reached its tick, and
/// the tick position is not pulled back to that tick when it does. So a tempo
/// change takes effect up to one sample's worth of the *old* tempo's ticks
/// late, and those ticks carry into the new tempo.
///
/// At ordinary tempos a sample is a small fraction of a tick and none of this
/// can be heard. It is audible in a black MIDI tempo trick: at 26,666 bpm and
/// 1920 PPQ a sample at 48 kHz is 17.8 ticks, so a 22 bpm segment after it
/// loses up to 17.8 x 1.42 ms. A reported file's burst of sixteen tempo changes
/// comes out 45.95 ms short in BASSMIDI, the file's author treats that version
/// as the correct one, and Kestrel used to play it exactly -- 45 ms behind
/// BASSMIDI for the rest of the song. Measured 2026-09-17 on 76 synthetic
/// sections through BASSMIDI at 48 kHz; every one matches this rule to within
/// 0.1 ms, including how the loss moves with the fast segment's length.
///
/// The integer part of every conversion is exact, so a change that lands on a
/// sample boundary carries nothing, as BASSMIDI's does not. Only the carried
/// overshoot is floating point.
///
/// **Cheap per event, which is most of the design.** The drain calls
/// `frame_at` once for every event in the file -- 1.65 billion on the densest
/// file measured -- so everything that only changes with the tempo is worked
/// out in `set_tempo`, and an event costs one 64-bit multiply and divide. The
/// first version recomputed the ratio and divided in 128 bits on every call,
/// and it put 3.7 s on the 14 s drain of a 45-million-note file (2026-09-17).
