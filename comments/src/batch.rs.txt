//! Several renders in one go: N MIDIs make N files, each with the soundfont
//! set it was given.
//!
//! A batch is not a new way to render. Every job is a [`Job`] run through
//! [`session::run`], so **its file is byte-identical to the same MIDI rendered
//! by itself**; what a batch adds is the order and the loading.
//!
//! - **Sequential.** One job on the device at a time. The card is already
//!   mostly busy on a normal render and its memory is the limit, so two at once
//!   would buy little and risk the card.
//! - **Grouped by soundfont set.** A set is the ordered soundfont list with its
//!   `sf_programs`. Each distinct set is loaded once, its jobs run back to back,
//!   and it is dropped before the next set loads, so two big sets are never
//!   resident together. Results are still reported in the order the jobs were
//!   listed.
//! - **A job that fails does not stop the batch.** It is recorded with its
//!   reason and the rest run. A set that cannot be loaded fails every job that
//!   uses it, and only those.
//! - **A file in progress is `<name>.partial.<ext>`** and takes its real name
//!   when the job finishes, so a cancelled batch never leaves something that
//!   looks complete. The extension is kept last because it picks the container.
//!
//! Everything a job shares comes from one template [`Job`] -- the command line's
//! flags -- and an [`Entry`] changes only what differs per job: the MIDI, its
//! soundfonts, where it goes, and how many seconds of it to render. Anything
//! that changes how a soundfont loads is shared by construction, which is what
//! lets a loaded set serve every job that names it.
//!
//! The same [`Entry`] list comes from the command line (`render a.mid b.mid`),
//! from a batch file ([`File`]), from the guided renderer and from the API.
