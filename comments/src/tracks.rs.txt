//! What each track of a MIDI holds, read before a per-track render is set up.
//!
//! A normal render merges every track into one stream and learns what the file
//! holds as it plays. A per-track render has to know before it starts: which
//! tracks carry notes, how many at each velocity -- so `--min-velocity` can be
//! applied to the voice split before any track renders, and a track it would
//! empty is skipped rather than written as a silent file -- and which carry
//! only controllers. It also needs the whole file's tempo map, because every
//! track is timed by it, whichever track the FF 51 events sit on.
//!
//! **Never merged.** MTrk chunks are independent, so each track is read on its
//! own, by one of several threads, largest first. The merge is what makes a
//! normal read cost `log2(track_count)` per event (see `MidiStream::next`);
//! without it a track costs only its own decode. A track is always read start
//! to finish by one thread, so the scan comes out the same whatever the
//! thread count, and only the time differs.

/// The per-block candidate cap each track of a per-track render gets, from
/// its own config once its voices are settled: 64 candidates a pool slot,
/// at least 2^16 and at most a 256th of `max_block_candidates`.
///
/// A render's own cap, 2^27, is a memory budget for one render -- about 4.5
/// GiB when a block reaches it -- and a per-track render has up to 256 in
/// flight, each keeping its list's high-water mark. At the full cap, 256
/// tracks of the largest file tested held 25 GB three minutes in
/// (2026-09-23). A
/// block admits at most a pool's worth, so 64 times that is ample to rank
/// from; a normal render's own cap is about 100 a slot at its default pool.
/// Past the cap a block is thinned evenly (`Driver::thin_cands`).
///
/// `--track` and `--tracks` both use it, so a stem is still exactly its track
/// rendered alone at the same voices.
